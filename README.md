# Identifying and Addressing Issues in the Refactoring of LLM-Generated Code

This project detects three readability issues in Python code written by large
language models, locates them down to the line, recommends a refactoring for
each, applies the safe ones automatically, checks that the refactored programs
still behave the same, and measures whether the code actually got better.

The three issues:

| Issue | Rule (in `generate_dataset.py`) |
|---|---|
| Long statement | a simple statement longer than 60 characters, measured as if written on one line |
| Nested loop | a `for`/`while` loop that contains another loop |
| Complex conditional | an `if`/`elif`/`while` test with 3 or more atomic conditions |

## Pipeline

| Stage | What it does | File |
|---|---|---|
| 1. Corpus | 800 LLM-generated programs with a manifest | `program_corpus/`, `build_corpus.py` |
| 2. Validation | syntax, duplicates and near-duplicate groups | `validate_corpus.py` |
| 3. Dataset | one row per statement with AST features and rule labels | `generate_dataset.py` |
| 4. Audit | label distributions and examples for review | `audit_dataset.py` |
| 5. Model | multi-output Random Forest, program-level split, evaluation | `train_model.py` |
| 6. Detection and localization | issues per program and line span, with confidence | `localization.py` |
| 7. Recommendation | a refactoring that fits each issue's code, and whether it can be automated | `recommendation.py` |
| 8. Transformation | applies the automatable refactorings to the source | `transformation.py` |
| 9. Validation | self-tests, differential testing, safety checks | `validation.py` |
| 10. Evaluation | issue resolution and independent quality metrics, before vs after | `quality_metrics.py` |

`main.py` runs stages 5-10 in one go on the held-out test programs.

## Dataset

- **Corpus:** 800 programs (`P0001`-`P0800`), 100 in each of 8 categories:
  none, each issue alone, each pair, and all three. They were generated by
  Claude Opus 5.5 (550) and Gemini 2.5 Pro (250) across 10 domains. Each
  program has an `if __name__ == "__main__":` block with asserts (its self-test).
  The corpus is frozen; `python build_corpus.py` checks it.
- **`dataset.csv`:** 8,358 statement records. 1,664 of them (about 20%) carry an
  issue: 730 long statements, 507 nested loops, 427 complex conditionals.
  Most statements in any program are ordinary code, and the corpus deliberately
  includes near misses (50-60 character statements, 2-part conditions).

## Setup

Requires Python 3.13.

```bash
python -m venv .venv
source .venv/bin/activate          # Windows: .venv\Scripts\activate
pip install -r requirements.txt
```

## Running

Whole pipeline (stages 5-10, about 30 seconds):

```bash
python main.py
```

It prints a short report per stage and writes the final programs to
`results/validated_programs/` and a combined `results/pipeline_summary.json`.

Each stage can also be run on its own and writes its detailed results:

```bash
python build_corpus.py        # check the finished corpus
python validate_corpus.py     # stage 2  -> corpus_validation.csv
python generate_dataset.py    # stage 3  -> dataset.csv
python audit_dataset.py       # stage 4
python train_model.py         # stage 5  -> results/model_evaluation.json, ...
python localization.py        # stage 6  -> results/localized_issues.json, ...
python recommendation.py      # stage 7  -> results/recommendations.json, ...
python transformation.py      # stage 8  -> results/refactored_programs/, ...
python validation.py          # stage 9  -> results/validation_report.json (about 80 s, includes the mutation check)
python quality_metrics.py     # stage 10 -> results/quality_evaluation.json, quality_metrics.csv
```

All scripts can be run from any directory. Results are deterministic (fixed
random seed).

## How the main stages work

**Stage 5, model.** Features are 8 numeric AST measures plus the statement
type. Programs are split with `StratifiedGroupKFold` (5 folds, fold 0 held
out): 640 training and 160 test programs, with near-duplicate programs kept on
the same side and every category in the test set. Also reported: grouped
5-fold cross-validation and a cross-model check (train on one LLM's programs,
test on the other's).

**Stage 6, localization.** Each predicted issue is tied to its program, file and
line span, and the span is verified against the source file. Predictions that
are impossible for the statement type (for example "nested loop" on an
assignment) are dropped.

**Stage 7, recommendation.** The refactoring depends on the code's shape: split
arithmetic, split `and`/`or` chains, extract arguments or list/dict elements,
replace an inline `if`/`else`, extract an `if`/`elif` condition, extract a `while`
predicate, flatten loops with `itertools.product`, or move an inner loop into a
helper. Issues inside the `__main__` self-test block are left unchanged.

**Stage 8, transformation.** Edits are made on the source lines (comments and
formatting elsewhere are kept), bottom-up, re-parsing after each edit.
Implemented refactorings keep evaluation order and short-circuiting:
- long arithmetic and `and`/`or` chains are built up in short steps;
- `if`/`elif` conditions are computed into a named variable (an `elif` becomes
  `else:` + `if`, so it is only evaluated when the earlier branches fail);
- perfectly nested, independent `for` loops become one `itertools.product`
  loop, only when that provably cannot change behaviour.

**Stage 9, validation.** For each refactored program: the code parses, its
self-test passes, and differential testing compares the original and the
refactored functions on the self-test's recorded calls plus edge-case
variants (zero, negative, empty, missing keys, ...). Classes are compared by
method traces. Safety checks require unchanged signatures, `__main__` block and
imports, and identical call counts. Failing programs keep their original form.
A mutation check plants faults in the refactored lines to measure how many the
validation catches.

**Stage 10, evaluation.** Target issues before and after (by the rules and by
re-running the model), and independent metrics: cyclomatic and cognitive
complexity, maintainability index, Halstead volume and difficulty, logical
lines, nesting depth, statement length and conditions per test, with paired
Wilcoxon signed-rank tests and the effect of each kind of refactoring.

## Results (160 held-out programs)

| Step | Count |
|---|---|
| Issues detected and localized | 352 (all at the correct line) |
| Left unchanged (inside `__main__` self-tests) | 49 |
| Automatable | 195 |
| Applied | 192 |
| Accepted by validation | 192 (115 of 115 programs pass; 3,467 calls compared, 0 mismatches) |
| Programs changed | 114 |

| Issue (outside `__main__`) | Before | After | Resolved |
|---|---|---|---|
| Long statement | 118 | 65 | 70% (29 new ones introduced) |
| Nested loop | 100 | 70 | 33% |
| Complex conditional | 85 | 4 | 95% |

Independent metrics (all changes p < 0.05): cyclomatic complexity, Halstead
volume, nesting depth, statement length and conditions per test improve;
cognitive complexity, maintainability index and logical lines get worse.
Loop flattening improves every metric it changes; condition extraction is the
main cause of the worse cognitive complexity and maintainability index.

The mutation check catches 237 of 286 planted faults (83%).

## Limitations

- **Rule-based labels.** The labels are produced by the rules above, and the
  model is given the features the rules are built on, so it learns the rules
  and scores near 100%. This is a consistency check, not a claim of high
  accuracy. Removing the defining feature drops F1 to about 0.73; the
  cross-model check gives complex-conditional F1 0.969.
- **Two generating models.** The corpus comes from Claude and Gemini only, and
  their styles differ.
- **Not yet automated.** Moving an inner loop into a helper (70 held-out
  issues), extracting arguments or elements, and `while` predicates are
  recommended but not applied.
- **Test inputs.** Differential testing uses inputs derived from each program's
  self-test, so some faults (17% in the mutation check) go unnoticed.
